# Git 工作报告编写规范

## 1. 报告定位

报告服务于工作汇报，不是提交日志的机械翻译。最终答复就是可直接发送的周报正文，不附带采集说明、生成总结、原始数据或操作建议。正文重点回答做了什么、涉及哪个项目或模块、目前处于什么状态。

## 2. 时间和统计口径

- 使用配置中的时区，默认 `Asia/Shanghai`。
- “上周”指上一个自然周周一 00:00 至本周一 00:00。
- “本周”指本周一 00:00 至报告生成时刻。
- “最近 N 天”是滚动的 N×24 小时，不能和自然周混用。
- 明确日期范围采用左闭右开区间，报告顶部写出解析后的开始、结束、时区和生成时间。
- 默认只统计已提交内容；未提交修改单独标记，不进入已完成工作。

## 3. 项目分区和主体结构

报告必须按项目拆分，并把“本期完成工作”放在每个项目的首位。默认结构如下：

```text
工作周报（统计周期）

项目 A
  本期完成工作
    工作主题
      具体事项
  待跟进（确有内容时）

项目 B
  本期无匹配提交

跨项目事项（确有内容时）
```

配置中的项目按“项目排序”输出。没有匹配提交的项目显示“本期无匹配提交”，读取失败时在该项目末尾简要写明原因。单仓库多子项目按“统计路径”归属；一个提交同时修改多个项目时，各项目章节写对应子改动，只在确有跨项目协同时增加“跨项目事项”。

默认不输出整体概览、统计口径、代码行数和提交明细。用户明确要求统计或明细时，放在周报主体之后，不能挤占“本期完成工作”的篇幅。

## 4. 作者识别

优先匹配 `Author` 的邮箱，邮箱统一转小写。姓名只在配置明确允许时作为备用匹配。`Committer` 只用于说明提交动作，不自动计入贡献。正文中不展示邮箱和完整本地路径。无法确认的作者不纳入用户工作，但要在异常说明中列出作者名和提交数量。

## 5. 去重规则

- 同一仓库、同一哈希在多个分支出现，只计一次。
- 同一仓库中 Cherry-pick 产生的同补丁，使用稳定 `patch-id` 识别，正文合并描述，明细保留全部哈希。
- 标题相同但文件和行为不同，不得去重。
- 多个提交构成同一功能时，可以合并为一个工作项，但必须保留所有来源提交。
- 不同项目默认不去重；相似功能属于不同项目时分开记录。
- 目录迁移、格式化、样式、文档、配置和重构提交不能被当成噪声删除。

去重是减少重复表达，不是减少事实。每个来源提交都必须落到正式工作项、合并工作项或待核实工作项中。

## 6. 工作项归类

按“项目 → 工作主题 → 具体事项”归类。一个工作主题覆盖同一业务目标下的多个提交，具体事项保留不同动作和结果。每个项目通常整理为 3—8 个主题，内容较少时不强行凑数。

常用主题包括：

- 新功能：新增页面、接口、字段、流程、组件或模块。
- 问题修复：修复错误、校验、权限、数据同步或兼容问题。
- 体验调整：表单、列表、提示、样式、交互和响应式调整。
- 结构调整：目录迁移、组件拆分、公共能力抽离、引用修正。
- 文档与配置：PRD、联调文档、字典、权限和环境配置。
- 待核实：标题或差异不足以准确判断实际效果的提交。

不要把 `feat`、`fix` 等提交类型直接当成工作内容。先看提交正文、文件路径和必要差异，再用业务语言归纳。相同目标的提交合并表达，独立行为必须保留；不能为了简短删掉样式、配置、迁移、重构或修复工作。

## 7. 状态和证据

默认使用“本期完成的改动”，不自动写“已上线”“已验收”“测试通过”。只有存在明确证据时才使用这些状态。未合入主分支的提交标记为“未合入”或“分支工作”。详情中出现“开发中”、TODO、空实现或占位内容时，列入待完善事项。

## 8. 非 Git 工作

用户提供的会议、评审、方案、联调、排查、测试和发布支持，标记为“人工补充”，并放入对应项目。没有来源的非代码工作不应编造。代码行数只作为统计参考，不作为工作价值判断；目录迁移和格式化造成的增删行应单独说明。

## 9. 去除 AI 味

优先使用“新增、调整、修复、迁移、补充、拆分、统一、限制、支持”等具体动词。避免“全面赋能、持续推进、进一步提升、形成闭环、夯实基础、显著增强、围绕重点工作”等空泛表达。不要逐条复述提交标题，也不要让每个句子都以“完成了”开头。每条工作说明写清动作、范围和可验证结果，不夸大影响。

最终答复禁止出现以下非周报内容：

- “已生成”“整理如下”“根据 Git 提交”等开场说明。
- 采集命令、执行过程、临时数据、验证过程和工具名称。
- 对报告质量的自我评价。
- “需要的话可以继续调整”等结尾邀请。

## 10. 默认报告模板

```markdown
# 工作周报（YYYY-MM-DD 至 YYYY-MM-DD）

## 项目名称

### 本期完成工作

- 工作主题
  - 具体事项一。
  - 具体事项二。

### 待跟进

- 仅列有提交、代码或人工补充依据的事项；没有则省略本节。

## 另一个项目

- 本期无匹配提交。

## 跨项目事项

- 只有确实涉及多个项目时才显示本节。
```

用户明确要求提交统计或明细时，再在主体后追加精简附录。
