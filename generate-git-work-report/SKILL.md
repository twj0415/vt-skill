# Git 工作报告

## 目标

将 Git 记录整理为可直接发送的中文工作报告。默认只读取本地数据，不拉取远程、不修改仓库、不把未提交修改当成已完成工作。最终答复只保留周报主体，不夹带采集过程、解释或建议。

## 强制确认

生成周报必须分为“确认范围”和“确认后执行”两个独立回合，不能跳过：

1. 收到“生成周报”“生成上周周报”等请求后，只读取本 Skill 的配置和编写规范，解析统计周期、项目、作者、分支、未提交工作、远程操作和输出范围。
2. 先向用户复述具体范围，并明确要求回复“确认生成”。此时禁止运行任何 Git 命令，包括仓库发现、`git status`、`git log` 和分支扫描。
3. 只有用户在后续回复中明确表示“确认”“确认生成”“开始执行”或“按这个生成”，才能读取仓库并生成报告。同一条初始请求中附带的确认不能跳过范围复述。
4. 用户修改任一范围后，重新复述完整范围并再次等待确认。确认只对当前范围和当前生成任务有效，不能沿用到下一次请求。
5. 信息缺失时列出缺项，不猜测作者、项目或时间范围。

## 确认后执行

1. 运行 `scripts/collect-git-work.ps1` 获取结构化数据。优先使用 `pwsh`，不可用时使用 Windows PowerShell。
2. 直接接收脚本标准输出并在内存中解析 JSON。禁止使用 `-OutputPath`，禁止在项目目录、Skill 目录或系统临时目录生成中间 JSON、日志或文本文件。
3. 按配置中的作者邮箱匹配 `Author`。不要只凭姓名猜测归属；无法确认的作者和提交保留为异常信息。
4. 按提交哈希去除分支重复，按稳定 `patch-id` 标记同一仓库中的 Cherry-pick 重复。去重只合并表达，不删除来源哈希或独立改动。
5. 检查提交标题、正文、修改文件和必要差异，补充笼统标题没有表达出的实际工作。不能根据代码臆测上线、测试通过或业务效果。
6. 按“项目 → 工作主题 → 具体事项”归类。每条属于用户的提交必须关联到一个工作项、合并工作项或“待核实工作项”。
7. 执行完整性检查：`属于用户的唯一提交数 = 已归类提交数 + 待核实提交数`。项目读取失败、仓库过浅或存在未识别作者时，在对应项目末尾简要说明。
8. 为每个配置项目生成独立章节。没有匹配提交的配置项目显示“本期无匹配提交”，不能静默跳过。
9. 只使用具体动词和可验证事实，删除重复表达和宣传式措辞。正文隐藏邮箱、完整本地路径和提交哈希。

## 运行脚本

示例：

```powershell
pwsh -NoProfile -File "<skill-dir>\scripts\collect-git-work.ps1" -Period 上周
pwsh -NoProfile -File "<skill-dir>\scripts\collect-git-work.ps1" -Period 最近7天
pwsh -NoProfile -File "<skill-dir>\scripts\collect-git-work.ps1" -Start 2026-08-01 -End 2026-08-14
```

需要临时统计未写入配置的当前仓库时，传入 `-RepositoryPath` 和 `-ProjectName`。脚本只向标准输出返回 JSON；直接解析输出，不落盘，也不把原始 JSON 交付给用户。

## 非 Git 工作

Git 无法记录会议、方案、评审、联调、排查、发布支持等工作。用户提供补充事项时，将其标记为“人工补充”，放入对应项目；没有用户提供时不要自行编造。

## 证据边界

- 提交代码只能写“新增、调整、修复、迁移、补充”等事实。
- 只有明确的测试命令、测试提交或用户说明，才能写测试结果。
- 只有标签、发布记录或用户说明，才能写上线结果。
- 未合入主分支的提交标记为分支工作或待合入，不写成正式发布。
- 未提交修改默认单列或忽略，不写成已完成工作。

## 输出要求

最终答复必须使用简体中文，并遵守以下要求：

- 除系统或用户级规则强制要求的称呼外，直接输出周报标题和正文。
- 不写“已为你生成”“采集完成”“数据来源如下”等开场白，不复述执行过程，不在结尾追加解释、建议或邀请。
- 默认结构为“项目名称 → 本期完成工作 → 工作主题 → 具体事项”，`本期完成工作` 是主体。
- 按项目分区；每个工作主题下保留足够具体的工作内容，合并重复表达但不能遗漏独立改动。
- 只有确有内容时才显示“待跟进”和“跨项目事项”。统计信息、统计口径和提交明细默认不输出，用户明确要求时再附加。
- 详细规则见 `references/周报编写规范.md`。
