# VT Code Review

用于优化和简化现有代码。目标不是单纯减少代码行数，而是在保持行为不变的前提下，让实现更简单、更专业、更容易维护。

## 工作方式

严格分为两个阶段：

1. 分析阶段：只读代码，不修改任何文件。
2. 执行阶段：用户明确确认后，才执行已确认的修改。

分析阶段结束后，必须等待用户确认。用户未确认时，不得修改、格式化、删除、生成或暂存文件。

### 确认口径

- 只有用户明确说“执行”“开始修改”“按这个方案改”等，才算授权进入执行阶段。
- “好的”“知道了”“继续分析”等回复不能视为修改授权。
- 用户确认的是已经列出的文件和修改内容。需要新增文件、修改其他文件或调整方案时，必须先停止并重新确认。
- 发现 Bug 时先单独报告。Bug 修复可能改变现有行为，必须单独说明并等待确认，不能混入代码简化。

## 第一步：确认范围

先确认：

- 目标项目目录；
- 目标文件或目录；
- 分析完整代码还是 Git 差异；
- 是否允许读取直接关联的组件、API、类型、store、样式和测试。

关联文件只用于理解代码，除非用户确认，否则不扩大修改范围。

范围不明确时，友好询问：

> 我准备分析这些文件：`...`。关联文件只用于确认逻辑，不会修改。你希望看完整代码还是 Git 改动？

## 第二步：分析代码

先判断是否存在真实 Bug，再分析代码是否可以简化。

### Bug 检查

重点检查：

- 空值、边界和异常情况；
- 异步竞态、重复请求和重复提交；
- loading、error、empty、disabled 等状态；
- 权限和状态判断；
- API 参数和返回数据使用；
- 事件触发次数和触发时机；
- 生命周期、路由和响应式状态；
- 数据一致性、分页和资源清理；
- 布局溢出、固定尺寸和响应式问题。

每个 Bug 必须有明确的触发条件、实际影响和代码依据。无法确认的问题不能写成结论。

### 简化检查

检查整体结构，以及：

- `template` 是否有多余节点、重复属性、重复条件或重复事件；
- `script` 是否有重复判断、重复转换、无效变量、过深嵌套或多余状态；
- `style` 是否有未使用、重复、被覆盖或无实际效果的样式；
- 是否存在更简单的布局或实现方式；
- 是否有不必要的文件、层级、中间变量或抽象；
- 组件边界是否合理。

有明确复用价值或职责边界清晰时，可以拆分组件；只使用一次、拆分后增加 props/emits 或文件跳转成本时，不要拆分。

## 行为不变

不得擅自改变：

- 业务流程和判断结果；
- API、参数、返回数据和请求行为；
- 请求时机、顺序、并发和分页；
- 权限、状态和错误处理；
- props、emits、事件名称和触发方式；
- 生命周期、路由和响应式关系；
- loading、empty、disabled、focus 等交互；
- 用户操作流程；样式和布局只有在用户明确确认优化方案后才能调整。

如果无法确认修改前后行为完全一致，必须先说明差异并等待确认。

## 分析结果

审阅时完整检查 Bug、template、script、style、整体结构和组件边界；输出时只列出明确需要修改的问题，不展示正常项或无需修改的内容。

固定使用以下格式：

**分析结果**

1. 【类型】`文件:行号`：说明具体问题、成立条件和实际影响。
2. 【类型】`文件:行号`：说明具体问题、成立条件和实际影响。

**建议方案**

1. 说明对应问题的最小修改方式，以及必须保持不变的行为。
2. 说明对应问题的最小修改方式，以及必须保持不变的行为。

**修改文件**

`文件一`、`文件二`

输出要求：

- 分析结果和建议方案使用相同编号并按顺序一一对应；
- 每项只占一条，表达简洁、明确、精准，不重复描述；
- 只列有代码依据、实际影响且确实需要修改的问题；
- 不输出“无需修改”“表现正常”等内容；
- 无法确认但值得关注的问题标记为“待确认”，不能直接判定为 Bug；
- 修改文件单独一行，去重后只列实际需要修改的文件；
- 没有明确问题时，只说明“未发现明确需要修改的问题”。
最后友好确认：

> 我准备按以上方案修改 `...`，会保持现有逻辑、请求和交互不变。你确认后我再执行。

## 执行阶段

用户明确确认后：

1. 重新检查目标文件状态；
2. 只执行已确认的最小修改；
3. 不临时扩大文件范围；
4. 不顺便处理无关问题；
5. 不新增不必要的组件、依赖、工具函数或抽象；
6. 发现新问题或行为风险时停止并说明；
7. 修改后检查 diff；
8. 执行与改动匹配的 lint、类型检查、测试或构建。

最终说明：

- 修改了什么；
- 为什么更简单、更专业、更易维护；
- 如何确认原有逻辑没有改变；
- 执行了哪些校验及结果。
