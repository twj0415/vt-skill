# JavaScript 与 TypeScript 规范

## 总原则

先尊重项目语言选择。TypeScript 项目写 TypeScript，JavaScript 项目写 JavaScript，不为了个人偏好强制迁移。

## TypeScript 项目

优先明确模块边界、外部输入输出和复杂业务对象类型：

- 组件 props
- emits 参数
- API 请求参数
- API 响应数据
- Pinia state
- 复用工具函数入参和返回值
- 复杂业务对象

业务类型在定义上方写一行用途说明，关键字段注释放在字段同一行。适用于表单状态、弹窗参数、API DTO、Props、Emits、快照和配置对象。示例只说明写法，不代表当前模块必须有相同字段。

```ts
// 列表查询参数
interface FeatureQueryParams {
  keyword?: string // 关键词
  status?: string // 状态
  pageNo?: number // 页码
  pageSize?: number // 每页数量
}
```

字段注释保持简短，说明业务含义、数据来源或特殊约束。如果当前接口存在大整数 ID、版本号、JSON 字符串或只读回显字段，再注明对应限制；不存在时不要补充这些说明。

不要给显而易见的局部变量、简单临时返回值补冗余类型。

## 类型组织

- 当前文件专用的简单类型可以写在当前文件。
- 已有类型目录优先沿用。
- 多处复用、语义稳定且当前文件放不下时，再拆到 `types.ts` 或业务类型目录。
- 避免超长内联类型。
- API 响应类型要靠近 API 模块或业务域。

## any 使用

- 不优先使用 `any`。
- 无法确认外部数据结构时，用 `unknown` 或临时窄化。
- 使用 `any` 时必须有明确理由，不要为了省事掩盖类型问题。

## JavaScript 项目

- 不强行加入 TS 类型语法。
- 保持和项目已有代码风格一致。
- 仅在数据结构不直观或 IDE 提示收益明显时，添加 JSDoc 或数据结构注释。

## 代码风格

- 函数命名表达业务含义，但不要重复目录、文件、组件上下文。
- 布尔变量使用 `is`、`has`、`can`、`should` 等前缀。
- 不为不影响本次需求的旧命名单独重命名。
- 避免魔法字符串和魔法数字；只有复用、业务含义明确或影响阅读时才抽常量。
- 注释解释业务用途、原因、限制或副作用；不要复述明显的实现步骤。
- 业务方法写一行用途说明，普通局部变量和简单语句不机械补注释。
- 详细注释规则见 `references/comments.md`。

## 格式化与 Lint

- JS / TS 编码风格保持项目内一致。
- 遵循项目已有 ESLint、Prettier 或格式化工具。
- 不因为补规则就强制安装新的 lint 包；项目已有配置优先。
