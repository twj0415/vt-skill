# 组件设计规范

## 核心原则

组件设计优先服务阅读和维护，不为了组件化而组件化。简单页面、简单交互、简单业务块优先直接写清楚；只有复杂度真的上来，拆分后更好读、更好维护时才拆。

判断标准：

- 主流程是否能从上到下顺着读懂。
- 拆分后是否减少了单文件复杂度。
- 拆分后 props、emits、状态同步是否仍然简单。
- 拆分后是否需要频繁跳文件才能理解业务。
- 组件边界是否稳定、清楚、符合当前项目风格。

## 组件职责

组件分层用于处理复杂度，不是固定模板。

- 页面组件负责路由级组织、数据装配和页面状态。
- 业务组件负责独立业务块。
- 基础组件负责纯 UI 和通用交互。
- composable 负责稳定可复用逻辑，或明显能降低页面复杂度的独立逻辑。

简单页面可以把页面结构、局部状态和少量方法放在同一个 `.vue` 文件内，不要为了符合分层而强行拆组件、拆 composable、拆类型文件或常量文件。

## 什么时候拆组件

适合拆分组件的情况：

- 单个 `.vue` 文件明显过长，已经影响阅读。
- 模板结构复杂，拆出后主流程更清楚。
- 某块 UI 已经稳定复用，或复用边界非常明确。
- 某块业务状态、事件、生命周期相对独立，且拆出后 props/emits 不复杂。
- 某个区域有独立 loading、empty、error、pagination、表单校验等完整状态，拆出后更容易维护。

拆分后必须满足：

- 父组件主流程更清楚。
- 子组件职责单一，命名明确。
- props/emits 简单直接。
- 不隐藏关键业务逻辑。
- 不为了复用引入很多配置参数、模式参数或回调参数。

## 什么时候不要拆组件

以下情况不要拆：

- 只是几行简单 DOM。
- 只是当前页面使用，且内容短小直观。
- 局部顺序逻辑放在一起更容易理解。
- 拆分只是为了让目录看起来更规范。
- 拆分后 props/emits 明显变多。
- 拆分后父子组件之间需要频繁同步状态。
- 拆分后业务上下文更难理解。
- 拆分后阅读主流程需要频繁跳文件。
- 两块 UI 只是长得像，但业务含义、状态或交互不同。

## 目录组织

目录组织按复杂度递进，不要一开始就套完整模块结构。

### 简单页面

简单页面优先保持简单：

```text
feature-name.vue
```

或：

```text
feature-name/
  index.vue
```

适用情况：

- 页面结构简单。
- 子区域不多。
- 状态和方法不复杂。
- 没有稳定复用的子组件、类型、常量或 composable。

### 中等模块

页面内容变多，但还没有复杂到需要多层目录时，核心业务块优先放在模块根目录：

```text
feature-name/
  index.vue
  Form.vue
  Detail.vue
  components/
    StatusTag.vue
    Toolbar.vue
```

规则：

- `index.vue` 作为当前页面或模块入口，负责组合页面结构和主流程。
- `Form.vue`、`Detail.vue`、`List.vue`、`Table.vue`、`Dialog.vue` 这类模块核心业务块优先放在模块根目录。
- `components/` 只放当前模块内部更细、更辅助的组件。
- 不要把所有组件都塞进 `components/`，避免核心阅读路径变长。
- 子组件数量少时，不必继续拆子目录。
- 少量模块私有类型、常量、状态映射、helper 可以留在 `index.vue` 或相关组件内。

### 复杂模块

只有模块特别大、子模块明显增多、文件职责已经混杂时，才使用更完整的结构：

```text
feature-name/
  index.vue
  Form.vue
  Detail.vue
  List.vue
  components/
    FieldItem.vue
    StatusTag.vue
    Toolbar.vue
  composables/
    useFeatureQuery.ts
  constants.ts
  types.ts
```

规则：

- 模块核心业务块放模块根目录，命名保持短而明确。
- `components/` 只放更细的辅助组件、局部展示组件或局部交互组件。
- `composables/` 只放稳定复用逻辑，或明显能降低页面复杂度的独立逻辑。
- `constants.ts` 只在常量、枚举映射、状态文案明显变多或被多处复用时创建。
- `types.ts` 只在类型定义明显变多、被多个文件复用或影响主文件阅读时创建。
- 跨模块复用组件放项目已有公共组件目录。
- 跨模块复用逻辑放项目已有公共 composables 或工具目录。
- 不要为了一个小功能单独创建完整目录结构。

## 共享基础组件边界

共享基础 UI 组件必须保持纯粹：

- 通过 props 传参，通过 emit 抛事件。
- 不直接调用业务 API。
- 不直接修改全局状态。
- 不写死业务字段、权限码、页面路由。
- 不依赖具体业务 store。

业务字段映射、权限判断、接口协议适配应放在页面、模块 composable 或模块层，不放进基础组件。

## Props 和 Emits

Props 表达输入，emits 表达事件。接口越简单，组件越容易维护。

- props 不承担内部状态职责。
- props 数量过多时，优先检查组件是否拆得太细或职责太多。
- 对象 props 要明确结构。
- emits 不传递模糊 payload。
- 事件名使用项目已有命名风格。
- 子组件不直接修改父组件状态。
- 不要为了拆组件导致 props/emits 数量明显增加。
- 如果子组件需要大量透传父组件状态，优先考虑不拆。
- 事件 payload 优先传必要字段，不要传整个复杂对象，除非业务确实需要。
- Props 字段使用同行短注释说明业务含义，Emits 事件说明触发时机和参数。
- 业务组件、弹窗和抽屉在文件或模板注册处说明职责；不要只靠组件名猜用途。

## 表单组件

表单设计优先清楚、直接，不要默认抽成独立组件。

- 简单表单可以直接写在页面内。
- 字段多、校验复杂、复用明确或多处共用时，才抽成独立表单组件。
- 区分表单数据、校验规则、提交状态。
- loading、error、disabled 状态要明确。
- 提交前处理重复点击。
- 表单弹窗关闭时是否重置数据要符合业务。

## 列表组件

列表设计优先保证状态完整和阅读清楚。

- 简单列表直接在页面内渲染即可，不要为了表格区域单独拆组件。
- 列表列配置复杂、操作复杂、状态独立或多处复用时，才抽成列表组件。
- 处理 loading、empty、error、pagination 或 load more。
- 列表 key 必须稳定。
- 大列表注意性能。

## 弹窗组件

弹窗设计优先简单，避免把一次性弹窗做成复杂组件。

- 简单确认弹窗优先使用项目已有弹窗能力。
- 表单弹窗字段少、只在当前页面使用时，可以保留在页面内。
- 弹窗状态复杂、表单复杂或多处复用时，才抽成独立组件。
- visible/open 状态来源要清楚。
- 关闭、确认、取消事件要明确。
- 关闭时是否重置数据要符合业务。
- 弹窗打开参数、成功事件、关闭事件和业务确认事件要写清楚用途。
- 如果组件存在版本过期、冲突确认等特殊事件，再说明触发条件和处理结果。
- 父组件连续注册多个弹窗时，在模板中分别标注各自的业务用途。
