# 简洁代码与文件组织

## 核心原则

写容易维护、容易顺着读下去的代码。优先简单直接，不为了显得高级而增加抽象、拆分、层级或复杂写法。

判断标准：

- 代码是否能从上到下顺着读懂。
- 主流程是否清楚，是否需要频繁跳文件。
- 抽象、拆分、命名是否降低了理解成本。
- 写法是否符合当前项目已有风格。

## 代码表达

优先使用最短、最直接、最容易读的写法。

- 能直接写清楚，就不要绕一层抽象。
- 能一行表达清楚，就不要拆成三行。
- 能一个判断解决，就不要拆成多个判断。
- 能用普通变量、普通函数解决，就不要引入复杂模式。
- 能提前返回，就不要写深层嵌套。
- 简单映射、过滤、取值可以直接写；复杂链式调用影响阅读时再拆开。
- 临时变量只在能提升可读性时使用，不为了“步骤完整”强行声明。
- 不为了函数式、设计模式或类型技巧牺牲直观性。

示例：

```ts
// 不推荐
const isStatusValid = status === 'active';
const isUserAllowed = user.canEdit;
if (isStatusValid && isUserAllowed) {
  submitForm();
}

// 推荐
if (status === 'active' && user.canEdit) submitForm();
```

## 抽象、拆分和复用

不要为了“可复用”提前抽象，也不要为了“看起来规范”提前拆分。只有拆分后更好读、更好维护时才拆。

可以考虑抽离的情况：

- 函数过长、职责混杂或嵌套过深。
- 相同 UI 或逻辑稳定复用达到 3 处。
- 复用达到 2 处且边界已经清楚。
- 重复请求、重复数据转换、重复过滤逻辑已经稳定出现。
- 格式化时间、格式化金额、状态映射、通用校验这类稳定通用方法。

抽离必须满足：

- 同源、稳定、边界清楚。
- 抽出后调用方更简单。
- 抽出后不隐藏关键业务逻辑。
- 抽出后不需要新增很多配置参数、模式参数或回调参数。

以下情况不要抽离：

- 只在当前组件内使用，且逻辑短小直观。
- 局部顺序逻辑放在一起更容易理解。
- 抽离后需要频繁跳转文件才能理解业务流程。
- 抽离后参数明显变多，调用方更难读。
- 两段代码只是表面相似，但业务含义不同。
- 抽离只是让代码看起来更“高级”，没有降低理解成本。
- 为了追求统一而大面积改动无关旧代码。

## 文件组织

文件组织优先服务业务阅读路径，不要机械按类型拆文件，也不要把小功能拆成很多小模块。

### 页面和组件

- 简单页面、简单组件优先单文件或少量文件完成，不要预设复杂目录结构。
- 只有模块特别大、子模块明显增多、文件职责已经混杂时，才按业务子模块拆目录。
- 模块私有的小类型、小常量、小 helper 可以留在当前组件或当前模块文件内。
- 类型、常量、composable、helper 只有被多处复用、内容明显变多或边界稳定时，才拆到独立文件。
- 拆文件后如果阅读主流程需要频繁跳转，优先保留在原文件附近。

### 工具函数

- 通用工具函数放在 `utils/` 或项目已有工具目录。
- 模块私有 helper 优先放在模块附近，不要直接丢进全局 `utils/`。
- 只有跨页面、跨模块复用且语义稳定的方法，才放到全局工具目录。
- 不要把业务强相关逻辑伪装成通用工具函数。

### API 文件

API 请求放在 `api/`、`services/` 或项目已有请求层，但不要过度拆分。

- 按业务大模块组织 API，例如 `user`、`order`、`system`。
- 同一业务域接口较少时，放在同一个 API 文件里更好读。
- 模块很大、接口数量明显增多、业务边界清楚时，再继续拆小模块或多层级。
- 不要为了一个很小的功能单独新建一层 API 模块。
- 不要把一个小接口拆成一个独立文件，除非项目已有这种明确约定。

## 命名

命名要语义明确，但不要无限变长。目标是让人一眼知道用途，同时读起来不累。

命名优先利用上下文：

- 目录名、文件名、组件名已经表达的信息，不要在变量、函数、组件名里重复写。
- 模块根目录内的核心文件优先使用短名，例如 `Form.vue`、`Detail.vue`、`index.vue`。
- 只有同目录存在命名冲突，或短名无法表达业务差异时，才加业务前缀，例如 `UserForm.vue`、`RoleForm.vue`。
- 不要默认写成 `UserManagementForm.vue`、`UserManagementDetail.vue` 这类长命名。
- `components/` 只放更细的辅助组件，命名也保持短而明确，例如 `StatusTag.vue`、`FieldItem.vue`、`Toolbar.vue`。
- 在组件内部，不重复写组件名。例如 `UserEditDialog.vue` 内可使用 `openDialog`、`closeDialog`、`submitForm`。

基础规则：

- 组件名表达业务角色。
- 函数名用动词开头。
- 布尔值使用 `is`、`has`、`can`、`should`。
- 避免 `data`、`list`、`temp` 这类过于模糊的命名，除非上下文非常清楚。
- `handleXxx` 只用于模板事件处理层，不用于业务动作、请求动作或数据转换。
- 业务动作使用准确动词，例如 `submitForm`、`loadOrders`、`formatRows`、`openDialog`。
- 缩写只用于团队熟悉的通用词，例如 `ID`、`URL`、`API`。不要自造难懂缩写。

命名过长时按顺序处理：

1. 先删除目录、文件、组件上下文中已经表达过的信息。
2. 再删除实现细节，例如 `FromServer`、`ToTableData`，除非确实有区分价值。
3. 如果仍然超过 3～5 个英文单词或读起来很绕，再检查是否职责过多，需要拆分。

示例：

```text
不推荐：UserManagementPageSearchConditionFormComponent.vue
推荐：user-management/components/SearchForm.vue

不推荐：handleClickSubmitUserCreateFormButton
推荐：handleSubmitClick + submitForm

不推荐：getOrderListDataFromServerAndFormatToTableData
推荐：loadOrders + formatRows

不推荐：submitUserManagementCreateUserDialogForm
推荐：submitForm
```

## 注释

不追求零注释。注释目标是让业务代码、动态表单、流程节点、配置型文件更快被理解。

允许短中文扫读型注释，例如：

```ts
// 新增
// 删除
// 获取登录配置
```

只在以下情况写注释：

- 解释业务原因。
- 解释兼容性限制。
- 解释临时方案和后续计划。
- 解释不直观的边界条件。

不要注释代码表面行为。
