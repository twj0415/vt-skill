# 注释与代码审阅规范

## 核心原则

注释帮助审阅者快速看懂业务，不追求数量。

- 命名说明“是什么”，注释补充“做什么、为什么、有什么限制”。
- 使用简短中文，一般一行说清楚。
- 注释必须与当前代码一致，逻辑变化后同步更新或删除。
- 不用注释掩盖模糊命名，名称不清楚时先改名。
- 示例只说明写法，不代表当前模块必须存在这些字段、状态或流程。
- 先阅读当前代码和接口文档，再决定是否需要某类注释。

## 类型和字段

业务类型在定义上方说明用途，字段注释放在字段同一行。

```ts
// 新增/编辑表单数据
interface FeatureFormState {
  id?: string | number // 数据 ID
  name: string // 名称
  status?: string // 状态
  version?: number // 数据版本号
}
```

以下类型需要说明用途和关键字段：

- 表单状态和弹窗打开参数。
- Props 和 Emits。
- API 请求参数和响应数据。
- 配置、树节点、快照等不直观的数据结构。

简单局部类型、字段名已经完整表达含义的类型，不机械补注释。

类型名称必须体现业务上下文。优先使用 `FeatureFormOpenData`、`FeatureFormState`、`OptionItem`，避免脱离上下文后含义不清的 `OpenData`、`FormState`、`Item`、`data`。

## Props 和 Emits

Props 说明输入数据，Emits 说明触发时机和参数。

```ts
defineProps<{
  record: RecordVO // 当前数据
}>()

const emit = defineEmits<{
  register: [] // 注册弹窗或抽屉
  success: [] // 保存成功
  change: [value: string] // 值发生变化
}>()
```

框架固定事件在同一组件内说明一次即可，不重复解释。

## 状态和配置

含义不明显、参与业务流程的状态写同行注释。

```ts
const pendingPayload = ref<SaveRequest>() // 重试时使用的待提交参数
const expandedIds = ref<Set<string>>(new Set()) // 已展开的数据 ID
const loaded = ref(false) // 是否完成首次请求
```

`loading`、`title` 等含义明确的状态不需要注释。

## 方法

查询、提交、业务操作和非直观转换在方法上方写一行说明。

```ts
// 加载列表数据
async function loadList() {}

// 打开新增弹窗
function handleCreate() {}

// 将表单数据转换为接口参数
function buildPayload() {}

// 确认后重新提交
async function handleConfirm() {}
```

以下方法需要注释：

- 查询列表、详情和下拉数据。
- 打开弹窗、抽屉或业务页面。
- 新增、编辑、删除、取消、提交等业务操作。
- 表单校验、提交和请求参数转换。
- 确认、重试、版本刷新等流程处理。
- JSON 解析、快照转换、层级组装和非直观状态同步。

简单 getter、格式化方法、明显的重置和单行赋值方法不机械补注释。

## Vue 模板

复杂模板按业务区域写注释，不给每个布局标签写注释。

```html
<!-- 顶部操作区 -->

<!-- 查询条件区 -->

<!-- 主内容区 -->

<!-- 列表加载状态 -->

<!-- 弹窗和抽屉 -->
```

局部组件可以使用：

```html
<!-- 卡片头部：名称、状态和操作 -->

<!-- 数据列表 -->

<!-- 操作记录 -->
```

不要写 `flex 布局容器`、`外层 div`、`按钮区域 div` 这类只复述结构的注释。不要在连续的 `v-if`、`v-else-if`、`v-else` 节点之间插入注释。

## 业务组件

弹窗、抽屉和用途不直观的组件，在组件标签前说明业务用途。

```html
<!-- 填写确认信息的弹窗 -->
<ConfirmForm @register="registerConfirm" @confirm="handleConfirm" />

<!-- 数据详情抽屉 -->
<DetailDrawer @register="registerDetail" @success="loadList" />
```

多个同类组件连续注册时，每个组件分别说明用途。组件事件只说明当前代码真实存在的事件，不凭示例添加事件。

## 业务规则

代码能看出行为但看不出原因时，写一行说明。只说明当前接口、权限或业务确实存在的规则。

```ts
// 保留原值，避免转换造成精度丢失
send({ id: record.id })

// 重试时沿用首次提交参数
pendingPayload.value = payload
```

以下情况按需说明，不是所有模块都必须存在：

- 大整数 ID 的传输限制。
- 版本号或乐观锁的提交要求。
- 业务错误码和确认重试流程。
- JSON 字符串、快照或动态配置的解析方式。
- 权限边界、状态限制和兼容性处理。

当前代码不存在这些约束时，不要自行添加字段、常量、注释或处理逻辑。

## 语言要求

直接写动作或业务名词：

```ts
// 加载列表
// 打开详情
// 校验日期
// 解析配置
// 重置展开状态
```

避免 AI 化表达：

- 该方法、该函数、本函数、此组件。
- 主要用于、负责进行、执行相关操作。
- 相关数据、数据处理、实现某某功能。
- 一段代码前写完整句式的重复说明。

## 审阅检查

- 类型名称是否体现业务用途。
- 业务类型和关键字段是否容易理解。
- 业务方法是否有简短说明。
- 主要模板区域是否有注释。
- 弹窗、抽屉和关键事件是否说明用途。
- 非直观业务规则是否说明原因。
- 是否把示例字段或示例流程套到了当前模块。
- 是否给普通布局和简单赋值写了多余注释。
- 是否存在 AI 化、过期或与代码冲突的注释。
