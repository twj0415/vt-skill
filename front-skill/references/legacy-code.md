# 旧代码处理与增量演进

## 默认原则

旧代码以最小必要改动为先。新增代码尽量遵守当前规范；触达旧代码时优先保持局部一致，不为了追求统一扩大改动范围。

## 局部一致优先

- 优先遵循当前目录、当前模块既有写法。
- 只在本次触达范围内做必要收口。
- 禁止跨目录强推单一风格。
- 不因为发现旧代码不理想，就顺手重写大面积无关逻辑。

## 增量演进

改旧页面时，只收口与本次需求直接相关的入口、分支或数据结构。旧结构不合适时，先指出问题，再做与当前任务相关的调整。

## 不做无关重写

不要为了理想形态重写无关代码。以下情况尤其要克制：

- 只是命名风格不同，但不影响本次需求。
- 旧代码结构大但本次只改小功能。
- 大范围替换会增加回归风险。
- 用户没有要求重构。

## 入口归一化

允许在边界入口做一次默认值归一化，主流程只消费规范化后的单一结构。

推荐：

```ts
const normalizedQuery = normalizeQuery(rawQuery)
```

主流程中不要散落多层兜底。

## 兼容逻辑

不要在业务主链路随意散落猜测式兼容：

```ts
a || b || c
foo?.bar ?? foo?.baz ?? foo?.value
```

兼容逻辑简单、只出现一次时，可以就近写清楚。多版本字段兼容复杂或多处使用时，再明确来源、边界和退出条件，并优先封装到入口归一化函数。

## 清理残留

只清理本次改动引入的残留，或触达范围内明确无用且低风险的问题：

- 无用 import
- 未使用变量
- 明确调试残留
- 已失效历史注释
- 不再服务业务的兼容代码

保留仍表达业务含义的现有中文注释；失真注释在触达范围内直接修正或删除。无关旧问题不要为了“顺手清理”扩大 diff。

## 验证

按风险选择最小必要验证。用户没有要求验证、改动很小且风险低时，不机械运行检查命令；无法验证时说明原因和建议。
