# 请求与数据流规范

## 核心原则

请求和数据流优先遵循项目已有封装和模块边界。简单局部逻辑保持直接，不为了“规范”强行新增 API 层、store、composable 或 mapper。

## 请求前检查

先定位本次触达的请求链路，再按缺失信息补查，不要每次全量扫描。

按需检查：

- 项目已有 request/http client。
- API 模块目录和命名风格。
- 错误处理封装。
- token 注入逻辑。
- loading 管理方式。
- 缓存或去重机制。

纯展示、纯样式、纯文案改动不需要检查请求链路。

## API 层

- 优先使用项目已有 `api/`、`services/`、request/http 封装。
- 不在组件里到处直接写 `fetch` 或 `axios`，除非项目现有风格就是页面内直接请求。
- 请求地址、公共参数、协议适配优先放 API 模块。
- 简单局部参数组装可以留在调用处，不强行抽函数。
- 不要为了一个很小的功能单独新建一层 API 模块。
- 组件负责调用和展示，不负责底层请求细节。

## 命名

命名优先沿用项目已有风格。没有明确约定时，再参考以下语义：

- 查询列表：`getList` / `getPage`
- 查询单条或详情：`getInfo` / `getDetail`
- 新增：`create`
- 修改：`update`
- 删除：`deleteItem` / `remove`，避免直接命名为 `delete`
- 批量删除：`deleteBatch`
- 状态修改：`updateState`
- 导入 / 导出：`importData` / `exportData`

同一模块内保持一致，不要同时混用 `getList`、`queryList`、`fetchList` 等同义命名。项目已有 `fetchXxx`、`queryXxx`、`getXxxApi` 风格时优先沿用。

## 状态处理

请求状态按页面实际交互需要处理，不要求每个请求都具备完整状态集。

常见状态包括：

- loading
- error
- empty
- refreshing
- pagination / hasMore

简单一次性请求可以只处理必要状态；用户可见失败必须有明确反馈。

## 避免重复请求

- 路由切换、弹窗打开、tab 切换时避免无意义重复请求。
- `onShow` / `onMounted` 中请求要判断是否真的需要刷新。
- 多页面使用相同数据时，只有重复成本、数据一致性或性能问题明确时，才考虑共享缓存、store 或 composable。

## 错误处理

- 不吞掉错误。
- 用户可见错误要给明确反馈。
- 开发者需要的错误信息要保留日志或调试信息。
- 不把后端错误结构硬编码到多个组件里；复杂或多处使用时再收口处理。

## 工具函数语义

- `resolveXxx`：根据输入推导结果，不产生副作用。
- `normalizeXxx`：把不稳定输入转成标准结构。
- `parseXxx`：解析字符串、协议、URL、配置。
- `formatXxx`：格式化展示文本。
- `createXxx`：创建对象、实例、配置。
- `applyXxx`：把结果应用到 DOM、状态、主题等，有副作用。
- `syncXxx`：同步两个状态源，通常有副作用。

## 数据转换

- 简单映射可以直接写在调用附近。
- 转换复杂、重复出现或需要单独测试时，再抽纯函数。
- 多处复用的 mapper 不重复写。
- 时间、金额、状态文案、枚举映射这类稳定通用转换可以统一处理。
